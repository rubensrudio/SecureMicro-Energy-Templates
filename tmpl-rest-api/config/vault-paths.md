# Vault Path Registry — tmpl-rest-api

**Requirement:** AC INI-14 (INI-US-03) — documentation of Vault paths per secret.
**Federal control:** RN-01 — Zero secrets in env vars, config files or VCS.
**Source:** plan.md section 4.1 — Secrets in Vault (KV v2).

---

## Overview

This document is the authoritative registry of every HashiCorp Vault path used
by the `tmpl-rest-api` service.  It maps each path to the secret key(s) it
contains, the consumer within the codebase, and the Spring property name that
receives the resolved value at startup.

All paths use the **KV secrets engine version 2** (`secret/` mount).

Spring Cloud Vault resolves these paths via:

```yaml
spring:
  config:
    import: "vault://secret/tmpl-rest-api/keycloak,vault://secret/tmpl-rest-api/service,vault://secret/tmpl-rest-api/db"
```

declared in `tmpl-rest-api/config/application.yml`.

> **IMPORTANT — fail-fast:** The import declaration does NOT use the
> `optional:` prefix.  If Vault is unreachable or any path is absent, the
> service refuses to start.  This implements the spec edge case:
> *"WHEN Vault is unavailable at startup THEN the service SHALL fail fast
> with a clear message."*

## Path Registry

### Path 1 — Keycloak Client Credentials

| Attribute       | Value                                              |
|-----------------|----------------------------------------------------|
| **Vault path**  | `secret/tmpl-rest-api/keycloak`                   |
| **Engine**      | KV v2 (`secret/` mount)                           |
| **Secret key**  | `client-secret`                                   |
| **Description** | OAuth2 confidential client secret used by the service to authenticate against the Keycloak token endpoint when performing client-credentials flows. |
| **Consumer**    | `shared-identity` — `IdentitySecurityConfiguration` |
| **Spring property** | `keycloak.client-secret`                      |
| **Referenced as** | `${keycloak.client-secret}` in `application.yml` |
| **Controls**    | RN-01, INI-10, INI-12                             |

**Write example (dev / quickstart):**

```bash
vault kv put secret/tmpl-rest-api/keycloak \
  client-secret="<replace-with-generated-secret>"
```

**Production notes:**
- The client secret is generated by Keycloak when the `tmpl-rest-api` client
  is registered.  Retrieve it from the Keycloak Admin Console or Admin API.
- Rotate by writing a new value to this path and performing an
  `/actuator/refresh` call or rolling restart (KV v2 has no lease renewal —
  see Risk R-01 in `plan.md`).

### Path 2 — Service API Key

| Attribute       | Value                                              |
|-----------------|----------------------------------------------------|
| **Vault path**  | `secret/tmpl-rest-api/service`                    |
| **Engine**      | KV v2 (`secret/` mount)                           |
| **Secret key**  | `api-key`                                         |
| **Description** | Internal API key used for service-to-service authentication when the service calls downstream APIs that require a static key rather than a JWT. |
| **Consumer**    | `tmpl-rest-api` — controllers and outbound HTTP clients |
| **Spring property** | `service.api-key`                             |
| **Referenced as** | `${service.api-key}` in `application.yml`      |
| **Controls**    | RN-01, INI-12                                     |

**Write example (dev / quickstart):**

```bash
vault kv put secret/tmpl-rest-api/service \
  api-key="<replace-with-generated-api-key>"
```

**Production notes:**
- Generate using a cryptographically secure random generator with at least
  128 bits of entropy (e.g. `openssl rand -hex 32`).
- Rotate by writing a new value to this path and performing an
  `/actuator/refresh` call or rolling restart.

### Path 3 — Database Credentials (Reserved)

| Attribute       | Value                                              |
|-----------------|----------------------------------------------------|
| **Vault path**  | `secret/tmpl-rest-api/db`                         |
| **Engine**      | KV v2 (`secret/` mount)                           |
| **Secret keys** | `username`, `password`                            |
| **Description** | Database credentials reserved for future database integration.  Phase 1 does not include a relational database; this path is seeded with placeholder values in the dev environment to keep the Vault import non-optional and consistent across environments. |
| **Consumer**    | `tmpl-rest-api` — reserved for future `DataSource` configuration |
| **Spring property** | `db.username`, `db.password` (Phase 2)        |
| **Referenced as** | `${db.username}`, `${db.password}` (Phase 2)  |
| **Controls**    | RN-01, INI-12                                     |

**Write example (dev / quickstart):**

```bash
vault kv put secret/tmpl-rest-api/db \
  username="placeholder-user" \
  password="<replace-with-generated-password>"
```

**Production notes:**
- Replace placeholder values before connecting to a real database.
- Consider using the Vault Database secrets engine (dynamic credentials) for
  production to achieve automatic rotation — this requires switching from KV v2
  to the Database engine and is planned for Phase 2.

## KV v2 Lease Renewal — Risk R-01

HashiCorp Vault KV secrets engine **version 2 does not issue leases**.
Spring Cloud Vault's lease-renewal mechanism applies only to dynamic secrets
engines (database, AWS, etc.).  For KV v2:

1. Write the new secret value to the Vault path.
2. Trigger a Spring Cloud refresh:
   - Call `POST /actuator/refresh` (requires `spring-cloud-starter` on the
     classpath and the `refresh` endpoint exposed).
   - Or perform a rolling restart of the service.

This constraint is documented as **Risk R-01** in `plan.md` (priority 1).

The `reference-deploy/vault/vault-dev-init.sh` script seeds all three paths
with development placeholder values when the Vault dev server starts.
